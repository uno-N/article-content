前回、ログイン試行のレート制限を「ログに記録するだけ」のモードでVercel Firewallに実装した話を書いた。

それから3週間、ログモードのまま放置していた。

今日、ようやく本番のブロックモードに切り替えた。でも、その決め手になったのは「完璧な分析ができたから」ではなかった。

---

## 0. なぜすぐに切り替えなかったか

ログイン試行を制限する仕組みは、間違えると諸刃の剣になる。設定が厳しすぎれば、正規のスタッフがロックアウトされる事故になりかねない。

このアプリは複数の訪問看護スタッフが使う。だから「1週間くらいログを見て、正規のログインが誤って引っかからないか確認してから、実際にブロックするモードに切り替えよう」と決めていた。

慎重なつもりだった。

---

## 1. 誤算：そもそも1週間分のログが存在しなかった

3週間後、いざログを確認しようとしてわかったことがある。

**Vercelの無料プラン（Hobby）では、そもそも1週間分のログが残っていない。**

- ランタイムログの保持期間は1時間
- Firewallダッシュボードの期間選択も「Live」「Past Hour」「Past Day」までしか選べない

「1週間ログを見てから判断する」という最初の計画は、無料プランの制約の前提を確認せずに立てた計画だった。1週間分のログを見るには、そもそも有料プランへのアップグレードが必要だった。

---

## 2. じゃあ、何を根拠に判断するか

完璧なログが手に入らない以上、手元にある材料で判断するしかない。整理してみた。

- **スタッフからの問い合わせ**：ログインで困ったという報告は、運用開始からゼロ件
- **Firewallダッシュボードのイベント**：見える範囲（直近1時間〜1日）で、異常なイベントは0件
- **実際のアクセス量**：直近1時間でAllowedリクエスト4件。そもそもの絶対数がかなり少ない

一つ一つは「証拠」というより「状況証拠」に近い。でも、積み重ねれば判断材料にはなる。

---

## 3. 気づき：モバイル中心のツールだから、IPが分散しやすい

レート制限は多くの場合「同じIPアドレスから来た回数」で数える。もし複数のスタッフが同じ職場のWi-Fiから接続していたら、それぞれは正常なログインをしているだけなのに、システムからは「同じ場所から複数回来た」とまとめてカウントされてしまうリスクがある。

このアプリは訪問看護の現場で使うモバイル中心のツールだ。スタッフは事業所のWi-Fiよりも、訪問先でスマホの回線から接続する場面の方が多い。つまり、**同じ人物が同じIPで何度もアクセスすることはあっても、複数人が同じIPに集中する場面は限定的**という前提が成り立つ。

「事業所で全員が固定回線から使う業務システム」と「訪問先からバラバラに繋ぐモバイルツール」では、レート制限のリスクの質が違う。この違いに気づけたのは、ログを見ようとして見れなかったからこそだった。

---

## 4. CLIでルールの中身を実際に覗いてみた

判断の最後のピースとして、設定していたルールの実際の閾値を確認した。

```bash
vercel firewall rules inspect "rule_login_rate_limit_log_u4A7yx" --json
```

```json
{
  "action": {
    "mitigate": {
      "action": "rate_limit",
      "rateLimit": {
        "limit": 5,
        "window": 60,
        "keys": ["ip"]
      }
    }
  }
}
```

**同じIPから60秒以内に6回目のログイン試行があったら検知**、という設定になっていた。

人が普通に使っていて、1分間に6回もログインボタンを押すことはまず起きない。閾値としてはかなり余裕がある。これなら誤検知のリスクは低い、と判断できた。

---

## 5. 決断：ログモードから、実際にブロックするモードへ

材料が揃った。

```bash
vercel firewall rules edit "rule_login_rate_limit_log_u4A7yx" \
  --action rate_limit \
  --rate-limit-action rate_limit \
  --yes

vercel firewall publish --yes
```

`log`（記録するだけ）から`rate_limit`（実際に制限する）へ。1分間に6回目のログイン試行からは、429エラーで弾かれるようになった。60秒経てばカウントはリセットされるので、正規ユーザーが万一引っかかっても、長時間ロックされることはない。

---

## 6. まとめ：完璧な情報を待っていたら、一生決断できない

最初の計画は「1週間分のログを見てから判断する」だった。でも実際には、そのログは存在しなかった。

もし「完璧なデータが揃うまで待つ」にこだわっていたら、このタスクはずっと期限を延ばし続けていたと思う。実際、最初の期限は3週間前に過ぎていた。

- 問い合わせの有無
- ダッシュボードで見える範囲のイベント
- サービスの利用実態（モバイル中心かどうか）
- ルールの閾値そのもの

理想的な形の証拠ではなくても、集められる材料を並べれば、意思決定はできる。個人開発だと「もっと確認してから」が延々と続きがちだけど、今あるデータで判断して、様子がおかしければまた戻せばいい——そのくらいの軽さで進めることも必要だと思った。
