前回、504エラーとの3週間の話を書きました。バックエンドを作り、ログインが通るようになって、「よし、これで一区切り」と思っていました。

でも商用化に向けて動き出すと、こう自問することになります。

**「本当に他の事業所のデータは見えないんだったっけ？」**

自分で作ったはずなのに、自信を持って即答できませんでした。だから、自分の実装を自分で監査することにしました。

結果、穴が2つ出てきました。

---

## 0. なぜ自分を疑うところから始めたか

このアプリは複数の訪問看護事業所が同じデータベースを共有する構成です。A事業所のスタッフが、B事業所の利用者データを見られてしまったら、事故では済みません。

「バックエンドのAPIでorgId（事業所ID）を絞り込んでいるから大丈夫」——そう思っていましたが、それは**アプリケーション側の実装が正しく動いている前提**の話です。実装にバグがあれば、その前提ごと崩れます。

なので、テーブルごとに「SELECT・INSERT・UPDATE・DELETEを誰ができるか」を一つずつ表にして、想定と実際のポリシー定義を突き合わせる作業をしました。

---

## 1. 穴①：同じ事業所の中でなら、誰でも他人を管理者にできた

最初に作った`staff`（スタッフ）テーブルの更新ポリシーはこうなっていました。

```sql
-- 旧ポリシー（migration 001）
CREATE POLICY "staff_update" ON staff
  FOR UPDATE TO authenticated
  USING (org_id = my_org_id());
```

一見、問題なさそうに見えます。「自分の事業所のスタッフ情報だけ更新できる」——狙い通りです。

でも、これは**「更新していい範囲」を絞っているだけで、「誰が更新できるか」を絞っていません**。

同じ事業所に所属してさえいれば、一般スタッフが他のスタッフのレコードを書き換えられます。当然、`role`列も対象です。つまり、一般スタッフが自分で自分のレコードを直接書き換えて、`role: 'admin'`にすることができました。

病院で例えると、「同じ病棟のカルテなら誰でも書き込める」状態です。担当看護師かどうか、医師かどうかは問われません。事業所という大きな括りでは正しく分離できていたのに、その中の権限の階層が抜けていました。

**修正：**

```sql
-- 新ポリシー（migration 007）
DROP POLICY IF EXISTS "staff_update" ON staff;

CREATE POLICY "staff_update_admin" ON staff
  FOR UPDATE TO authenticated
  USING (org_id = my_org_id() AND is_org_admin())
  WITH CHECK (org_id = my_org_id());
```

`is_org_admin()`を条件に足すだけです。管理者だけが、自分の事業所内のスタッフ情報を更新できるようになりました。

一行足りていなかっただけで、権限昇格が可能な状態になっていた——これが一番ヒヤッとした発見でした。

## 2. 穴②：塞いだはずのポリシーが、名前のズレで生き残っていた

もう一つは、監査ログ（`audit_logs`）まわりです。

このテーブルは「誰が・いつ・何をしたか」を記録する場所なので、ユーザーが直接書き込めてしまうと、ログの改ざんが可能になります。だから最初から「専用の関数を経由してしか書き込めない」設計にしていたつもりでした。

ところが、マイグレーションの履歴を辿るとこうなっていました。

```
migration 002：ポリシー "audit_insert" を作成
migration 006：ポリシー "audit_logs_insert"（別名）をDROP
```

**名前が違います。**

006を書いたとき、自分では「以前作ったINSERTポリシーを消して、関数経由だけに絞った」つもりでした。でも実際にDROPしたのは存在しない名前のポリシーで、002で作った本物の`audit_insert`はそのまま生き残っていました。

```sql
-- 実際に残っていたポリシー（002）
CREATE POLICY "audit_insert" ON audit_logs
  FOR INSERT TO authenticated
  WITH CHECK (org_id = my_org_id());
```

これのせいで、認証済みユーザーなら誰でも`audit_logs`に直接INSERTできる状態が、006を書いた後もずっと続いていました。「消したはず」が一番怖いパターンです。

**修正：**

```sql
-- migration 008
DROP POLICY IF EXISTS "audit_insert" ON audit_logs;

-- ポリシーだけでなく、テーブルレベルの権限自体も剥奪
REVOKE INSERT ON TABLE audit_logs FROM authenticated;
```

ポリシーを消すだけでなく、`REVOKE`でテーブルへの書き込み権限そのものを外しました。今後同じ名前ミスをしても、テーブル側で二重に塞がれています。

---

## 3. 番外編：レート制限が、サーバーレスでは機能していなかった

監査とは別に、ログイン試行のレート制限でも足をすくわれました。

最初はこう実装していました。

```typescript
const attempts = new Map() // IPごとの試行回数を覚えておく
```

ローカルで動かすと、ちゃんと5回失敗した時点でブロックされます。ところが本番（Vercel）にデプロイすると、何度失敗してもブロックされませんでした。

原因は、Vercelのようなサーバーレス環境の性質でした。

`Map`は「プログラムが動き続けている間だけ」記憶を保持します。ローカルでは1つのサーバーが起動しっぱなしなので問題になりません。でもサーバーレス環境では、リクエストのたびにどの実行インスタンスが処理するかは保証されず、インスタンス自体もしばらく使われないと消えて作り直されます。

病院の受付に例えると、窓口が複数あって、**それぞれの窓口が自分専用のメモ帳しか持っていない**ような状態です。A窓口で「この人はもう5回来た」とメモしても、次にB窓口に案内されたらそのメモは見えません。カウントが窓口ごとにバラバラなので、制限が実質機能しないのです。

これは「実装が甘かった」というより、サーバーレスは基本的に**ステートレス（状態を持たない）前提で作られている**、という性質そのものでした。インスタンスをまたいで共有する記憶が必要なら、外部の共有ストアが要ります。

**修正：** 自前でRedis等を用意する前に、Vercel Firewall（プラットフォーム側のレート制限機能）に切り替えました。個々の関数の中ではなく、リクエストが関数に届く前の入口で制限がかかる仕組みなので、この問題自体が起きません。今は挙動確認のため「ログのみ記録するモード」で1週間分の様子を見て、正規のログインが誤ってブロックされないことを確認してから、実際に制限をかけるモードに切り替える予定です。

---

## 4. 「バックエンドで絞っているから安全」だけに頼らない

ここまでの3つの穴は、どれも「アプリケーション側の実装」の話でした。バックエンドAPIがorgIdで絞り込んでいるから大丈夫、と思っていた前提そのものにバグがあったわけです。

だからこそ、RLS（Row Level Security）を**バックエンドの実装が正しいことを祈るための保険ではなく、実装が間違っていても最後に守ってくれる二枚目の壁**として位置づけています。

```
① バックエンドAPI：JWTのorgIdでデータを絞り込む（主防衛線）
② RLS：たとえ①を迂回されても、DB側で事業所をまたいだアクセスは通さない（保険）
```

今回見つかった2つの穴も、たとえバックエンドのロジックに同じような見落としが将来また起きたとしても、RLSさえ丁寧に作り込んでおけば最後の砦になります。実際、Threadsで「RLSさえ丁寧にやっておけば大丈夫だと思う」という反応をもらったのですが、まさにそれを裏付ける結果になりました。一つの壁を過信せず、壊れても次の壁がある状態を作っておくことが、結局一番効いています。

---

## 5. まとめ

| 見つけたもの | 何が問題だったか | 直し方 |
|---|---|---|
| staff_updateポリシー | 同一org内なら誰でも他人をadminに書き換え可能だった | admin限定の条件を追加 |
| audit_insertポリシー | 別名をDROPしたつもりが本物は残存、直接INSERT可能だった | 正しい名前でDROP＋REVOKEで二重に封鎖 |
| レート制限 | インメモリのMapがサーバーレスでは共有されない | プラットフォーム側の機能（Vercel Firewall）に切替 |

自分で設計して、自分で「大丈夫なはず」と思っていた場所ほど、疑ってみると穴があります。今回の教訓は、性善説で「たぶん大丈夫」を信じず、テーブル一つ・ポリシー一つ、実際に手を動かして確認することでした。
