## 1. なぜ分離が必要だったか

モニターが始まると、DBに入るのは他人の事業所の、他人の患者の薬剤情報になる。開発中のコードが本番DBを触れる状態のまま外部に渡すのはやってはいけない。今まで自分ひとりで使っている分には「壊したら自分で直す」で済んでいたが、それが通用しなくなる。

分けるべき場所は実は4箇所＋1箇所（後から気づいた）あった：

1. DB（Supabase）
2. デプロイ（Vercel：ブランチごとの環境）
3. Vercelの環境変数
4. フロントのrewrite設定
5. ローカルの`.env`／`.env.local`（手順書になかった。作業中に自分で気づいた見落とし）

DBだけ分けても、他が分かれていなければ「開発のつもりで本番を触る」事故が起き得る、という当たり前だけど見落としがちな構造。

## 2. データベースの階層構造（初めてちゃんと理解した）

```
データベース（プロジェクト1個）
  └─ スキーマ public（フォルダ）
       ├─ テーブル organizations（表）
       │    └─ カラム id, name, plan...（表の列）
       ├─ テーブル patients
       └─ テーブル staff
```

- **スキーマ**＝テーブルを入れる「フォルダ」。`public`はPostgresが新規DB作成時に自動で用意する、何も指定しなければテーブルが入るデフォルトの場所。自分で設定した覚えがなくても、裏側で自動的に存在している
- Supabaseは`public`以外に、ログイン機能用の`auth`、ファイル保存用の`storage`なども自動生成する

## 3. SQLの読み方（型を覚えると全部読める）

```sql
SELECT 何を FROM どこから WHERE 条件 ORDER BY 並び順;
```

これが分かれば、今回使ったクエリは全部読める。日本語の語順とほぼ同じ。

- `SELECT tablename, policyname, ...` → この項目を表示して
- `FROM pg_policies` → この名簿（Postgresが自動管理している「今存在する全RLSルールの一覧」）から
- `WHERE schemaname = 'public'` → ただしこの条件のものだけ
- `ORDER BY tablename, policyname` → この順番に並べて

## 4. NULL許可／NOT NULLの意味

- **NOT NULL**＝必ず値を入れないと保存できない
- **NULL許可**＝空のままでも保存できる

`org_id`（どの事業所のデータかを示す列）がNULL許可だと、「どの事業所か分からないデータ」がDBに紛れ込む余地がある。マルチテナント構成では地味に重要な設定。

## 5. RLS（Row Level Security）とは何か

「このテーブルのこの行は、どの条件を満たした人だけが見たり書き込んだりできる」というDB側のルール。たとえば「事業所Aのスタッフは事業所Aの患者データしか見られない」というルールがRLS。

ポリシーを見るときの読み方：

| 列名 | 意味 |
|---|---|
| `tablename` | どのテーブルへのルールか |
| `policyname` | ルールの名前 |
| `cmd` | SELECT/INSERT/UPDATE/DELETEのどれに対するルールか |
| `qual` | 見る・消すときの条件 |
| `with_check` | 追加・更新で新しく入れる値が満たすべき条件 |

### RLSの一番怖い性質：複数ポリシーは「OR判定」

同じテーブルに複数のポリシーがあると、**どれか1つでも条件を満たせば操作が許可される**。これが今回、2つの本番バグの原因になっていた。

**発見したバグ①：`staff`テーブルの権限昇格**

過去に「一般スタッフが自分をadmin roleに書き換えられる」バグを一度直した記録（マイグレーション007）があったのに、本番には`staff_all`という「同一事業所内なら管理者チェックなしで何でもできる」ポリシーが別途存在していた。RLSのOR判定により、せっかく直したはずの制限が実質無効化されていた。

**発見したバグ②：`unknown_drugs`の他事業所書き込み**

`authenticated users can insert unknown_drugs`というポリシーが`with_check: true`（条件なし）で存在していた。ログインさえしていれば、他事業所のorg_idを指定して書き込めてしまう状態だった。

**どちらも、ポリシー名の付け方から由来が分かった**

自分で書いたルールは全部`staff_delete`のような短いスネークケース名。でもこの2つだけ、`"authenticated users can insert unknown_drugs"`のような文章そのものの名前だった。これはSupabaseダッシュボードの「New Policy」テンプレートから直接作ったときに自動でつく名前のパターン。つまり**過去にエラーが起きたとき、ファイルを書く前にダッシュボードで応急処置し、書き写すのを忘れた**という事故の痕跡だった。名前の付け方のクセだけで、原因がある程度推理できるのが面白かった。

## 6. service_roleキーとRLSバイパスの話

RLSは本来「ログインしている本人が直接DBに話しかけてくる」ときのための壁。でも`zannyaku-api`の設計では、フロントは直接Supabaseと話さず、必ずバックエンド（API）を経由する。バックエンドは`service_role`という特別な鍵を使っていて、**RLSを完全にスルーする**。

これ自体は普通の設計（本当の壁はDBのRLSではなくAPIコードの正しさになる）。ただし重要な認識：

> RLSが効いていれば、APIのコードにバグがあって事業所の絞り込みを書き忘れても、DBが土壇場で弾いてくれる（2重の壁）。でもservice_roleだと、その2重目の壁が存在しない。

なので「新しいルートを追加するたびに、org_idの絞り込みを書き忘れていないか」は、DBが守ってくれない以上、毎回人間が確認するしかないポイント。これは`CLAUDE.md`にチェックリストとして明文化して、今後のレビューで毎回確認するようにした。

## 7. トリガーと関数：新規事業所登録が本番で壊れていた

`handle_new_user`という関数（新規ユーザー登録時にstaffテーブルへ自動で行を作る処理）は本番にも存在していた。でも、それを実際に呼び出す「配線」である`on_auth_user_created`トリガーが、**本番にだけ存在していなかった**。

関数という中身はあるのに、呼び出すスイッチが本番だけ繋がっていない状態。これに気づけたのは、本番・開発でトリガー一覧を照合したから（関数一覧の照合だけでは気づけなかった）。

影響：`/api/auth/register`（新規事業所登録）は、認証アカウントを作ったあとこのトリガーに依存してstaffレコードを作る設計だった。本番でこのトリガーが欠けていたので、**新規事業所が自己登録すると、アカウントだけ作られてstaffレコードが残らず、ログインできなくなる**状態だった。自分の事業所の3人は過去に手動SQLで作成されていたため、今まで気づかれずに済んでいた。

モニター展開の直前にこれが発覚したのは正直ヒヤッとした。

## 8. Vercelの仕組み：Project・Deployment・エイリアス

ここが一番、最初こんがらがった部分。

- **Project（プロジェクト）**＝設定だけを持つ「定義」。環境変数・ドメイン・ビルド設定などを保持する。それ自体はコードを実行しない
- **Deployment（デプロイ）**＝特定のGitコミットに紐づく、不変（immutable）のビルド成果物＋実行インスタンス。pushのたびに新しく1個作られる。古いものを上書きするのではなく、隣に増えていく
- **エイリアス（固定URL）**＝「今どのデプロイを指すか」を管理するポインタ。`zannyaku-v6.vercel.app`のような固定URLは、pushのたびに最新のデプロイへ自動的に向け直される

mainブランチからのpush→本番デプロイ、それ以外のブランチ（develop含め）からのpush→Previewデプロイ、という振り分けは、GitHub連携した時点でVercelが自動設定する「Production Branch」という設定に基づく。個別に何か設定した記憶がなくても、連携時点で自動で決まっている。

### 実際に起きた事故：`vercel link --yes`で別プロジェクトを誤作成

`.vercel/project.json`が存在しない状態で`vercel link --yes`を実行したら、既存の`zannyaku-v6`に繋がるはずが、ディレクトリ名と同じ**新しい空のプロジェクト「zannyaku-app」を誤って作成**してしまった。気づかずに進めていたら、本番とは別の宙に浮いたプロジェクトが残るところだった。「作成日時が数十秒前」という事実で誤作成に気づき、プロジェクト名を明示する`--project`オプションで正しく繋ぎ直した。

教訓：`vercel link`は、プロジェクトが存在しない場合は**黙って新規作成してしまう**。既存プロジェクトに繋ぐときは、プロジェクト名を明示するほうが安全。

## 9. ローカルの`.env`とVercelの環境変数は別物

ここも最初混同していた。

| 場所 | いつ使われるか |
|---|---|
| `zannyaku-api/.env`・`zannyaku-app/.env.local` | 自分のパソコンで`npm run dev`するとき。Vercelからは一切見えない |
| Vercelの環境変数 | develop/mainをpushして、Vercelのサーバー上でコードが動くとき |

今回のPreview/Production分離作業は、Vercel側の環境変数の話であって、ローカルの`.env`ファイルとは無関係。ただし確認したら、**ローカルの`.env`のSUPABASE_URLが本番を向いていた**ことが発覚。今まで手元での開発作業が、知らずに本番DBに直接触れていたことになる。Vercel側の分離が終わったら、ローカルもzannyaku-dev用の値に書き換える予定。
